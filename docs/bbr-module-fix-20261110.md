## 问题与修复

主菜单 `2` / `M1` 原先把 `tcp_available_congestion_control` 中没有 `bbr` 当作不支持，但该列表只包含已注册算法，未加载模块不会出现。现改为主菜单 `2` / `M1` 进入 BBR 管理页并自动只读显示运行内核、环境、当前算法、注册列表与状态；`1` 启用、`2` 查看状态、`0` 返回。状态直接读取内核 `/proc` 接口，不补装依赖或写入；已启用显示当前网络命名空间的默认算法。已注册时保留确认切换；未注册且未检测到容器时查询当前运行内核目录下的真实模块，经独立两次 `YES` 确认加载，再回读注册列表，另经两次 `YES` 启用。缺少普通模块查询/加载工具仍走既有 `y` 补装流程。

模块查询保留退出码，并区分 stderr 与合法文件名，拒绝 BusyBox 的退出码 0 空输出、诊断冒充路径、越界模块路径、内建却未注册等情况；不强制要求文本 `modules.dep`，兼容 kmod 的二进制索引。确认后重新核对内核、路径、当前算法和 BBR 可用状态；`modprobe` 不读取后续确认输入。加载后取消启用会保留模块并明确提示，不主动卸载。写入后回读失败会明确说明已尝试切换，不能称成功或已回滚。

LXC 等容器未注册 BBR 时，明确提示由宿主管理员或服务商提供，不查询或加载宿主模块；环境识别未知也拒绝模块加载。宿主已提供 BBR 时允许确认尝试切换，以实际 sysctl 权限和回读为准，不能保证所有容器可写。环境识别只使用已有 `systemd-detect-virt --container`、运行标记、PID 1 容器字段和 Docker/Podman/OpenVZ 标记，不安装 systemd。PID 1 环境完整经过管道，失败不当作非容器，原始内容不进日志或结果。

该开关仅改变当前网络命名空间、当前运行期的默认拥塞控制；主要用于后续新连接，不声称切换所有已有连接。，不写持久配置，不替换内核，不执行 `depmod` 或重启。B16 网络优化路径保持原状。

## 用户机器的诊断边界

用户提供 Alpine 3.21.10、运行内核 `6.18.58-0-virt`，当前算法 `cubic`，注册列表 `reno cubic`；`/lib/modules` 无输出、`linux-virt` 未安装，`modinfo` 报当前内核索引不存在。用户后续已明确确认这是 **LXC 容器**。它共用宿主内核，当前容器未获得已注册 BBR；缺本地模块目录不应通过容器内安装内核包解决。`0::/` 本身不能判断容器，身份确认来自用户。

因此本修复不能为这台机器凭空补出 BBR。应由宿主管理员或服务商核对并提供 BBR，之后容器中的启用还需实际写入权限；不要把无版本约束的 `apk add linux-virt` 当作普通 BBR 依赖修复。
